# Current frozen B legacy project

This explicit plugin supplies the current v4.3.2 GSE130563 intake and the
complete 23786-gene BH/BY family endpoint. Install it together with
`bulk-limma-normalized`. It does not use the older design ZIP resource registry
or its CONDITIONAL_EXPLORATORY roles. Its checked-in project lock records the
actual current configuration, manifest, sample/feature maps, discovery scope,
design and G0 certificates, software declarations, frozen scientific code,
rules, original byte verifier, restoration evidence, family lock and source
identities. Matrix/metadata hashes were taken from the frozen manifest;
this source preparation did not open or fit the actual assay matrix.

The locked B entry permits LEGACY_EXPLORATORY_FULL_FEATURE_DISEASE_ASSOCIATION.
It has no scientific signature or independent validation permission, and its
all-project scientific gates flag remains false. The adapter records SEEN
history and LEGACY_EXPLORATORY_PRIMARY_MODEL output roles. Numerical execution
does not convert this into formal science. This release covers the primary
`~group+age+sex` model; the frozen unadjusted and treatment sensitivities remain
separate prespecified analyses and are not executed by this graph.

Before real execution, run the original project `02_EXECUTION/verify_g0_v432.py`
read-only under its existing study access/ownership rules. This adapter checks
the B-required files against their original runtime manifest and source hashes;
it does not execute or replace that full-project verifier. Audits explicitly
record `original_full_project_byte_verifier_executed=false` and full-project
verification as false. Root/operator admission must supply that actual gate.
The original frozen scientific R program is hash-bound evidence. The numerical
nodes execute the separately preserved normalized limma component; they do
not claim to execute the whole frozen scientific program or its authorization
guards. SYN parity evidence must distinguish those scopes.
The old R component schema names one identity field `source_archive_sha256`;
for this independently reviewed project transport it carries the original
input-manifest SHA256. It is not presented as an old design ZIP identity.
The intake audit retains the actual separate project and source file hashes.

Generate the exact TUI `dag_shell` request without opening the study payload:

```sh
python3 -B tools/build_frozen_b_project_dag.py \
  --project-uri vfs://YOUR_APPROVED_PROJECT_MOUNT \
  --output /tmp/frozen-b-dag-shell.json
```

The generated request contains 19 hash-enabled source references and four
connected nodes: intake → DESIGN → LIMMA → full-family BH/BY. Submit its
`script` to `dag_shell` first with `dry_run=true`; after runtime installation,
source admission and the original project byte audit succeed, submit with
`dry_run=false`, then invoke `run_dag`. The generator does not execute either
step. No configuration JSON schema, port ordering or gene-family request needs
to be guessed. The terminal node publishes `family.tsv` and `family-audit.json`;
LIMMA also publishes its real `official.rds` and same-source audit.

Before deployment, the operator must mount the four declared artifact prefixes
to the study's approved output locations and bind each native run directory to
its run name and ledger. The proposed locations are
`research/results/v4.3.2/B_LEGACY_TUI/{intake,design,limma,family}` beneath the
project's top-level results area, outside the immutable
`versions/v4.3.2/bm_cachexia_v432_g0` baseline. The original byte verifier
compares the baseline's complete path set, so adding results inside that
baseline would invalidate it. These mounts are not
created or verified by the source generator. The graph adds no covering sink
